## Decisions
- 2026-09-09 1.9c: `IPersonAccountProvisioningService.CreateWithPhoneAsync` and `IInvitationRegistrationService.CreateUserWithPhoneAsync` now return (person id, IsNewAccount) instead of a bare id. Found because 1.9b's lock made two concurrent register-and-accept requests share one person: the loser, still believing `isNewAccount = true` from its lookup made before provisioning, compensated by soft-deleting the winner's account, and the concurrent HTTP test ended with no person at all. Before the lock the same flaw was masked — each request created its own person and the loser deleted its own. Tier 2 bug fix — flag for review.
- 2026-09-09 1.9b: the lock is `pg_advisory_xact_lock(hashtext(phone))` taken by `PersonProvisioningService` itself. Because the pipeline's TransactionBehavior wraps the ServiceCatalog context, not UserManagement's, the service opens its own transaction when none is ambient and flushes the new person before committing — so a sign-in that fails after provisioning leaves an account with no token, which the next sign-in reuses (the intended one-person-per-phone outcome). Rejected: waiting for the §1.2 unique index (blocked on production data), a session-level advisory lock (unsafe with pooling), and a claims table (a migration for what a lock does). Tier 2 — flag for review: the early flush changes when UserManagement domain events for a new person are dispatched (at provisioning rather than at the handler's final save; same in-context ordering as before). Verified by PersonProvisioningConcurrencyTests (3/3 green, previously 3/3 red).
- 2026-09-09 19.8a: `GetCurrentProviderStatusQuery` → `GetOwnedProviderStatusQuery`; the HTTP route `current/status` and the controller action name are unchanged, so no client changes. Tier 0.
- 2026-09-09 6.2b: pending invitations get their own `PendingInvitationsCubit` beside `StaffCubit` instead of a combined state, so a failed invitations read cannot blank the member roster (the screen falls back to "no pending"). Cancel uses the membership-native revoke route, not the hierarchy DELETE. No "resend" — the backend has no resend endpoint and the SMS link stays valid until expiry. Tier 1.
- 2026-09-09 5.3b: the legacy `/Providers/{id}/staff` endpoints are NOT deleted. They already delegate to membership handlers and have no client callers, but the keystone deploy gate (steps 1–5) and the Reqnroll StaffManagement feature exercise them; deleting the endpoints means deleting those tests first, which is a suite change owed its own task. Kept as documented shims. Tier 1.
- 2026-09-09 19.6: `CancelBooking`'s slot release stays unscoped by StaffId. It has no resolver, and `Booking.StaffId` is the organization id for a direct booking (matches no slot's StaffId), so scoping it would silently release nothing; the loop only touches slots carrying this booking's own BookingId, so unscoped is exact. Create/Reschedule are scoped through `BookableResource.SlotStaffId` (null for the organization booked directly). Tier 2 bug fix; 6 real-Postgres tests (`AvailabilityStaffIsolationTests`) + resolver unit tests.
- 2026-09-08 (migration) 1.9b: close the concurrent-create race in the application with a per-phone transaction-scoped lock rather than wait for the DB index (1.2), which is blocked on production data; the index remains the defense-in-depth backstop. Reversible.
- 2026-09-08 13.6c: invitation expiry is derived on read; no sweep job and no `Expired` audit entry until a state transition exists that needs auditing. Reversible.
- 2026-09-07 17.3: only Owner memberships are switchable in the app; staff-only memberships are listed but not switchable until a staff workspace exists (17.6).
- 2026-09-06 6.4: register-and-accept returns no session token; a new member signs in through the standard OTP flow. Minting a token there is additional backend scope.
- 2026-09-06 5.4: cross-context membership read is in-process raw SQL (mirrors PersonDirectoryReadService), deliberately not modelled on the HTTP self-calling IProviderInfoService.
- 2026-09-06 4.3: join-request approval grants the requester's owner a Manager membership additively (RequesterId is a ProviderId, not a PersonId); superseded by 19.1.
